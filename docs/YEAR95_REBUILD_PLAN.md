# YEAR95 — Plano Estrutural de Reconstrução\n\nStatus: arquitetura aprovada para a reconstrução; nenhum código de produção da aplicação nova foi considerado migrado automaticamente.\n\n## 1. Objetivo\nConstruir uma nova aplicação sob a marca YEAR95 usando o repositório atual como fonte de referência técnica e comportamental, sem transformar o projeto novo em um fork do legado.\n\nPrincípios:\n- reconstrução seletiva, não cópia integral;\n- preservar comportamento validado como contrato;\n- reescrever fronteiras onde o legado acumulou compatibilidade e caminhos legados;\n- Supabase/PostgreSQL permanece a base de dados;\n- frontend e backend nascem juntos e são validados ponta a ponta;\n- paper trading apenas no início;\n- nenhuma rota de ordem real;\n- provedores externos entram por adapters;\n- AI é advisory-only;\n- Risk Engine é determinístico e central;\n- cada PR precisa passar por gates de regressão.\n\n## 2. Estado observado da fonte\nRepositório de referência: engineiapt-ops/ai-financial-analyst\nHead atual auditado: e539b1583276c40b6793986d947134e82921ca74\nO repositório atual contém aproximadamente 300 arquivos versionados, cerca de 239 no diretório src, 23 migrações de banco e múltiplas camadas de API, market data, quant, risk, AI, research, evaluation, portfolio, paper trading, options e brokers.\nA fonte atual contém bons contratos, mas também acoplamento histórico, facades de compatibilidade e uma cadeia de testes/scripts muito grande. A reconstrução aproveita o conhecimento acumulado sem carregar esse acoplamento.\n\n## 3. Arquitetura alvo\n\nYEAR95/\n  apps/\n    api/                  # Express, HTTP, auth, orchestration\n    web/                  # React/Vite, dashboard e UX\n  packages/\n    contracts/            # Zod/domain DTOs compartilhados\n    domain/               # Instrument, Decision, Signal, Account, Evidence\n    quant/                # Indicadores e primitivas determinísticas\n    risk/                 # Risk Engine e políticas\n    market-data/          # Ports, normalização, qualidade, adapters\n    decision/             # Confluence + deterministic decision\n    paper-trading/        # Simulator e validação paper-only\n    ai/                   # Provider interface + Gemini adapter\n    persistence/          # Repositories e migrations\n    evaluation/           # Outcomes, KPIs, OOS e governance\n    backtest/             # Walk-forward somente depois do core\n    research/             # Point-in-time research, advisory\n    portfolio/            # Portfolio diagnostics/simulation\n    providers/            # IG/Saxo/etc. adapters, quando aprovados\n    config/               # Configuração validada\n  db/\n    migrations/\n  docs/\n  .github/\n\n## 4. Direção de dependência\nWeb / HTTP\n  ↓\nApplication services\n  ↓\nDomain\n  ↓\nPorts / contracts\n  ↓\nAdapters / persistence\n\nRegras:\n- domain não importa Express, pg, SDK de broker ou SDK de IA;\n- route handler não calcula indicador nem executa SQL complexo;\n- market-data provider nunca decide BUY/SELL;\n- Risk Engine não depende de UI;\n- AI nunca altera threshold, sizing ou autorização de execução;\n- paper-trading não depende de live broker;\n- repositories escondem SQL e conexão.\n\n## 5. End-to-end primeiro\nO primeiro marco funcional da YEAR95 será:\n1. login;\n2. frontend autenticado;\n3. frontend chama API;\n4. API valida identidade;\n5. API acessa Supabase/PostgreSQL;\n6. API responde health/readiness;\n7. frontend mostra estado real;\n8. market data BTCUSDT;\n9. persistência;\n10. deterministic analysis;\n11. risk decision;\n12. paper signal.\n\n## 6. Autenticação\nSeparar dois conceitos:\n- identidade de usuário: Supabase Auth;\n- acesso interno/serviço: secrets do backend, nunca no browser.\nO banco financeiro continua acessado pelo backend através de DATABASE_URL. Nenhuma tabela financeira será exposta diretamente ao browser.\n\n## 7. Market data\nCore inicial:\n- BTCUSDT;\n- candles fechados;\n- timeframes iniciais: 1h, 4h, 1d;\n- REST para histórico;\n- WebSocket para atualização de candle quando necessário;\n- normalização para contrato genérico Candle;\n- instrumento canônico separado de símbolos de provedores.\nA arquitetura será provider-agnostic desde o primeiro dia, mesmo começando com Binance.\n\n## 8. Quant + Decision\nO núcleo determinístico inicial deve reutilizar como referências os comportamentos já validados em:\n- price action;\n- VWAP;\n- RSI por zona;\n- ATR por timeframe;\n- detecção de lateralização/regime;\n- confluence;\n- risk/reward.\nO Decision Engine produz uma decisão estruturada: WAIT, BUY ou SELL, acompanhada de evidências e confiança.\nA decisão quantitativa permanece autoritativa.\n\n## 9. Risk Engine\nPolíticas de referência a preservar:\n- risco máximo por operação: 1% do equity;\n- R:R mínimo: 1:2;\n- posição/notional e risco são conceitos distintos;\n- dados inválidos ou stale falham fechado;\n- instrumento/provider não verificado falha fechado;\n- bloqueio de risco significa nenhuma executable signal.\nReferência de sizing:\n- base de 1,5% de exposição/notional;\n- componente dinâmico isolado;\n- nunca confundir positionNotionalPct com riskPerTradePct.\nQualquer alteração de política deve ser uma mudança explícita, testada e documentada.\n\n## 10. Paper trading\nMarket Data → Decision → Confluence → Risk → Paper Validation → Simulator → Outcome\nNão haverá criação de ordens reais, endpoint de ordem live, credencial privada de broker no frontend ou promoção automática de SIM para LIVE.\n\n## 11. AI\nInterface alvo:\nAiProvider\n  ├─ Gemini\n  └─ future providers\nGemini é o primeiro adapter.\nAI pode acrescentar contexto, narrativa, risk flags e watch items.\nAI não pode alterar thresholds, aumentar sizing, autorizar execução ou substituir a decisão quantitativa.\nToda saída externa passa por validação estrutural.\n\n## 12. Pesquisa, avaliação e governance\nEstas áreas ficam depois do core funcional:\n- point-in-time research;\n- decision outcomes;\n- calibration;\n- OOS policy;\n- walk-forward;\n- portfolio diagnostics;\n- pipeline audit;\n- system validation;\n- validation history;\n- continuous governance.\nOs contratos do legado são referências valiosas, mas serão reimplementados em módulos menores e coerentes.\n\n## 13. Infraestrutura\nEstratégia inicial:\n- Supabase: PostgreSQL persistente;\n- Render: backend/API inicialmente;\n- Cloudflare: domínio, DNS, edge e frontend/Pages quando conveniente;\n- Vercel: não é dependência estrutural da aplicação nova.\nA aplicação não deve depender de Vercel OIDC ou AI Gateway para funcionar.\n\n## 14. Observabilidade e segurança\nObrigatórios no core:\n- request id;\n- logs estruturados;\n- redaction de secrets;\n- rate limiting no backend;\n- CORS explícito;\n- validação de configuração;\n- health/readiness;\n- erros seguros;\n- timestamps explícitos;\n- auditoria dos eventos de decisão.\n\n## 15. Estratégia de testes\nQuatro camadas: unit, contract, integration e E2E.\nO novo projeto não repetirá o padrão de um único npm test gigantesco sem classificação.\nGates mínimos:\ntypecheck → unit → contract → integration → E2E crítico → build\nO deploy só é candidato depois de todos os gates verdes.\n\n## 16. O que não fazer\n- copiar 239 arquivos para a nova base;\n- transportar facades legadas;\n- levar endpoints obsoletos;\n- carregar compatibilidade apenas para satisfazer imports antigos;\n- misturar refactor com mudança de estratégia;\n- introduzir live trading durante a reconstrução;\n- adicionar opções, FX ou stocks antes do core BTC estar provado;\n- tornar o frontend dependente do backend Vercel;\n- alterar o Supabase estruturalmente sem migration plan.\n\n## 17. Critério de conclusão da reconstrução inicial\nlogin → dashboard → health/readiness → BTCUSDT data → persistência Supabase → deterministic analysis → risk decision → paper signal → evidence/audit\nCom testes unitários, integração e E2E verdes, sem live trading.
